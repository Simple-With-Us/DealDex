# 2026-10-15 — DD-369 `alert_runs` migration

Linear **DD-369** asked for `scan_runs` plus `alert_runs` alongside the manager-triggered `POST /api/alerts/run` cron.  `scan_runs`, the endpoint, and `.github/workflows/scan-runner.yml` landed in PR #341; this change adds the missing `alert_runs` table and persists one aggregate row per runner tick.

## What

- `migrations/0011_alert_runs.sql`: `alert_runs` keyed on `id` with `source`, `rules_ran`, `rules_skipped`, `dry_run_only`, `per_rule` JSON, timestamps, and optional `error`.
- `src/lib/server/alert-rules-store.ts`: `persistAlertRun` / `listRecentAlertRuns`.
- `src/lib/server/scan-runner.ts`: wraps each tick in Sentry span `scan.runner` and writes an `alert_runs` row after every invocation.
- `src/routes/api/alerts/run.ts`: accepts optional `source` in the JSON body (workflow sends `cron`).

## Env (document only — no new secrets)

Existing cron secrets unchanged: `SCAN_RUNNER_URL`, `SCAN_RUNNER_TOKEN` (GitHub Actions) and Infisical `SCAN_RUNNER_TOKEN` on the server.
